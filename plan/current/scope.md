## In Scope

- DAG scheduler with `blocked_by` dependency resolution and 2-second poll interval
- Cascading prune on `VIABILITY_REVIEW` score < 5, recursive across full branch
- Variational execution: 3 candidates per eligible task, judge model selection
- Go build validation (`go build` via `os/exec`) and self-correction feedback loop (max 5 retries)
- Sticky model strategy to minimise VRAM swap frequency
- `keep_alive: 0` enforcement on all Ollama calls (MAX_VRAM_MODELS = 1)
- Semantic router: 5 task types mapped to 5 Ollama models via config
- MCP client with 10 registered servers (Brave, GitHub, context-mode, fetch, Wikipedia, HN, mcp-reddit, ArXiv, YouTube Transcript, Memory)
- Custom `mcp-reddit` TypeScript MCP server with app-only OAuth and 429 backoff
- Context sidecar pattern: per-branch JSON files for accumulated context
- Context compression: SUMMARY task emitted at 70% context threshold
- DuckDB observability log (`obs.db`) + stdout mirror via `log/slog`
- Output artifact deposit to configurable project directory on terminal state
- `prune-report.md` generation for fully pruned projects
- Research-first task priority (DECOMPOSE → RESEARCH → VIABILITY_REVIEW primary flow)
- Agent Skills (agentskills.io format) for all task-type system prompts — 5 custom skills in `skills/`
- Official Anthropic skills bundled as reference: `mcp-builder`, `webapp-testing`
- Skill-loader in orchestrator: parses SKILL.md frontmatter, injects body as Ollama system prompt on dispatch

## Out of Scope

- Email dispatch (handled by external system consuming the output directory)
- Dropbox or cloud sync (handled by external system)
- Authentication or access control (local-only, single-operator tool)
- Multi-machine or distributed execution
- Cloud deployment or containerisation
- Web UI or dashboard (observability is DuckDB query + stdout only)
- Posting, voting, or commenting on Reddit (mcp-reddit is read-only)
- User-facing API (no HTTP server exposed)
- Automatic model pulling (`ollama pull` is operator responsibility)

## Deferred

- Job brief schema formalisation: the structure of the seed task `payload` is intentionally flexible; a formal schema may be defined in a future phase once usage patterns are established. Blocked: no formal validation of seed payloads until defined.
- Additional MCP server registrations beyond the initial 10: the config-driven MCP client supports future additions without code changes.
- Pagination for MCP tool responses: initial implementation returns single-page results; multi-page traversal deferred to a future iteration.
- Playwright MCP and Docker MCP: noted as candidates during P0; deferred pending validation that fetch + GitHub cover the primary use cases.
